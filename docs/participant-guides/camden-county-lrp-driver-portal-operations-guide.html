2. Claim, verify, and acknowledge

Requests begin unclaimed. Claim the record before working it so another staff member can see who owns the next step.

The available controls change with the request status and the action currently in progress.

  1. 1Select Claim request.

    Confirm the assignment shows you before making a status change.

  2. 2Verify the basics.

    Participant, verified phone, date, pickup/arrival timing, approved pickup, destination, companion, and notes.

  3. 3Choose the right status.

    Use Acknowledged when valid and ready for Moovs entry; Needs information when something is missing.

  4. 4Explain adverse outcomes.

    Declined requires a clear rider-visible reason. Cancelled is for a request that will not proceed.

There is no “Approve request” button. For a valid ride request, Acknowledged means “LRP reviewed it and is working on scheduling.” It is not a ride confirmation. Approve transportation is a separate participant eligibility control.

4. Let sync confirm—and clear exceptions

LRP Driver Portal checks Moovs on a 15-minute cadence. A pending request confirms automatically only when it finds one in-scope Moovs trip with both the exact reference and verified passenger phone.

1. AcknowledgeRequest is reviewed and ready to schedule.
2. Build in MoovsCorrect passenger, phone, route, time, and external reference.
3. Sync matchesExact reference + verified phone + allowed program scope.
4. ConfirmedRequest links to the trip and the participant receives confirmation SMS.

Use the reconciliation cards and request detail to investigate records that did not link cleanly.

Missing reference

Add the exact request reference to the Moovs External Reference Number field, then allow sync to retry.

Phone mismatch

Verify the Moovs passenger is the participant and correct the passenger phone. Never force a match by guessing.

Duplicate reference

Review every Moovs trip carrying the reference. Round trips can be valid; unintended duplicates must be corrected.

Linked

Moovs remains the pricing and operational source of truth. Multiple trip rows may link to one round-trip request.

Likely no-show: review the trip evidence, then choose Not a no-show or Confirm no-show. Add a concise audit note when context will help the next reviewer.

5. Process changes, cancellations, and messages

Participant actions remain attached to the original request. LRP Driver Portal records the conversation and audit trail; the actual operational change still happens in Moovs.

Sample fixture data. The rider-visible update and internal note serve different audiences.

  1. 1Claim and review the action.

    Read the participant's reason, timing, current Moovs trip, and action deadlines.

  2. 2Acknowledge the action.

    Tell the participant it is being handled; do not imply the Moovs change is complete yet.

  3. 3Update Moovs manually.

    Change or cancel the operational reservation and verify the result in Moovs.

  4. 4Complete the action in LRP Driver Portal.

    Record the participant-facing outcome and any necessary internal audit context.

Shared rider message
Visible to the participant and coordinator. Write clearly, professionally, and with no internal-only detail.

LRP-only note
Never shown to the participant/coordinator. Use for concise operational or audit context.

Messages and internal notes are immutable after submission. Review before saving. Portal v1 does not write changes or cancellations into Moovs automatically.

6. Manage participants through three separate gates

Transportation eligibility, portal login, and approved pickups are independent. Enabling one does not automatically enable the others.

A new participant starts pending, without a portal identity, and without an approved pickup.

1

Transportation eligibility

Approve transportation only after program authorization. Suspend/resume separately when eligibility changes.

2

Approved pickup

Add, approve, edit, and select a default pickup. The roster/source home address is reference-only—not automatically approved.

3

Portal login

Enable access only when the participant is ready. Suspend/reactivate login without changing transportation eligibility.

Safe onboarding order

  1. Verify identity and mobile phone.
  2. Approve transportation if authorized.
  3. Add and approve the pickup; set the default.
  4. Enable portal access and verify the user can sign in.

Before troubleshooting requests

  • Eligibility is active.
  • Portal login is active.
  • At least one pickup is approved.
  • Ride type and destination are allowed.
  • The verified phone is current.

Common trap: portal access alone does not make someone ride-ready. Without transportation approval and an approved pickup, the participant still cannot submit a valid request.

7. Keep locations and ride rules current

These settings control which routes participants can request and when the portal allows a request, change, or cancellation.

Left: destination review and catalog. Right: ride-type policy and service targets. Sample fixture data.

Locations

  • Review pending rider destinations before use.
  • Approve or reject with enough context for the audit trail.
  • Keep destination names, categories, addresses, and active status accurate.
  • Do not treat a roster home address as an approved pickup.

Ride types

  • Advance notice and same-day rules determine when requests are allowed.
  • Change/cancel cutoffs determine whether participant actions are available.
  • Acknowledge and confirmation targets drive queue urgency.
  • Policy changes affect future participant behavior immediately—verify before saving.

Configuration changes have program-wide impact. Confirm any policy or location change with the program owner before editing. Preserve the reason for material changes in the appropriate operational record.

8. Reporting and protected program setup

Use Reporting for evidence and exports. Use Program setup only for authorized administrative changes—not routine request processing.

Sample fixture data. Never share screenshots or exports outside approved program channels.

Reporting

  • Filter the correct period before reviewing totals.
  • Use linked Moovs costs and invoice evidence as the operational record.
  • Export CSV only when needed and store it in an approved location.
  • Payments and accounting actions remain outside the portal.

Program setup

  • Support phone, program dates, budgets, and report/SMS recipients.
  • Allowed Moovs company and booking contact IDs define integration scope.
  • These IDs are not request references.
  • Verify authorization and exact values before any change.

High-risk area: a wrong allowed company ID or booking contact ID can hide valid trips or pull the wrong records into reconciliation. Do not experiment. If uncertain, stop and verify with the program owner or integration administrator.

9. The complete request checklist

Use this sequence every time. The goal is a clean participant experience, a correct Moovs reservation, and an auditable LRP Driver Portal record.

  1. 1Claim the request.

    Confirm ownership before touching status or messages.

  2. 2Verify participant readiness.

    Eligibility, verified phone, approved pickup, destination, ride type, and timing.

  3. 3Read the full record.

    Route, appointment/arrival time, companion, notes, conversation, and active actions.

  4. 4Acknowledge—or ask.

    Acknowledge valid work. Use Needs information or Declined with a clear rider-visible explanation.

  5. 5Copy the reference.

    Paste the exact CC-… into Moovs External Reference Number.

  6. 6Build the Moovs reservation.

    Correct participant and phone, schedule, route, notes, company, and booking contact.

  7. 7Wait for the 15-minute sync.

    Do not manually claim confirmation. Confirmed follows a clean reference + phone match.

  8. 8Resolve any exception.

    Missing reference, phone mismatch, duplicates, or out-of-scope company/contact.

  9. 9Process follow-ups in both systems.

    Acknowledge in LRP Driver Portal, change/cancel in Moovs, then complete the portal action.

  10. 10Close the loop.

    Verify participant-facing status, record concise audit context, and clear the queue item.

The one-line rule: CC request reference goes in Moovs External Reference Number; the verified participant mobile goes on the Moovs passenger. When both match, sync does the rest.

Stop and verify when…

  • The participant phone differs between systems.
  • More than the expected trip rows use a reference.
  • The trip is not in the allowed company/contact scope.
  • Someone asks for a program-wide settings change.
  • You cannot tell whether a message is participant-visible.

Privacy and audit

  • LRP Driver Portal data is confidential.
  • Use only the information needed to schedule and support the ride.
  • Do not share exports, screenshots, or participant details in unapproved channels.
  • Never put credentials or secrets in notes.
  • Sign out or lock the device when finished.
